# v1.1 Step 1 — 诊断：为什么轻载下「像没用」

日期：2026-11-18  
输入：充分预热四组 spark（45s after Done + 30s after players + 30s profiler）

## 1. 稳态数据回顾

| 场景 | mean MSPT | 备注 |
|------|-----------|------|
| A 无插件 | 1.38 | 主线程 96%+ park |
| B 仅插件 | 1.44 | 差 **+0.06ms（噪声级）** |
| C 无插件+GD | 2.06 | |
| D 插件+GD | 2.07 | 差 +0.01ms |

TPS 全是 20。**轻载下不能证明插件「提速」**；甚至 B 略差。

## 2. 插件自己在干什么（B/D 日志）

稳态采样窗口内（约 10s / 200 tick）：

| 指标 | 典型值 | 折算 |
|------|--------|------|
| `pluginKick`（累计） | **0.8–1.2 ms / 窗口** | ≈ **0.004–0.006 ms/tick** |
| Preload `lastKick` | 0.04–0.05 ms/cycle | 每 20 tick 一次 |
| PathWarm `lastCycle` | 0.05–0.11 ms/cycle | 每 40 tick 一次 |
| Preload `started` | 持续增长（8k+） | 区块已加载时多为 no-op 规划 |
| PathWarm `queued` | **0** | 邻域区块都已加载，扫了但没事干 |

**结论**：插件主线程成本本身很小；B 比 A 差 0.06ms **无法用 pluginKick 解释**，更像噪声 / 调度 / GC。  
真正的问题是：

1. **空闲时仍在做无效扫描**（pathwarm 查实体、preload 规划矩形，结果 queued/started 增量为 0 或可忽略）。  
2. **测试场景没有多核可分摊的活**（无探索、无高粒子扇出压力）→ 插件「帮不上忙」是场景问题。  
3. 早期 −33% 是把启动尖峰算进 mean，**已作废**。

## 3. v1.1 目标（可验证）

| 目标 | 指标 |
|------|------|
| **G1 空闲更便宜** | 低 MSPT 且上轮「无事可做」时，拉长 pathwarm/preload 调度（**不是高负载暂停**） |
| **G2 减少无效实体扫描** | pathwarm 在明显无事时跳过 `getNearbyEntities` |
| **G3 小粒子不并行** | 观众/数量过小走顺序，避免 parallel 开销 |
| **G4 补压测场景** | 增加「多观众高频 particle + 连续区块加载」对照，证明多核有场景收益 |

**硬约束（不变）**：

- 高 MSPT **绝不**把模块跑到 0（不暂停）；空闲拉长间隔允许，且 `drain` 仍每 tick 跑。  
- 不改 AI、不改原版 `execute` 语义。
